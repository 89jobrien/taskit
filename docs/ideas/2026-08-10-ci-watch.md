# Idea: `ci-watch` — Live GitHub Actions Run Watcher

## Effort

Medium (1-3 days)

## Source

Grounded in `minibox/xtask/src/ci_watch.rs`.

## Problem

`taskit flow auto` polls a CI gate as part of its develop → staging →
release → main pipeline (per `CLAUDE.md`'s Architecture section: "flow auto =
promote + CI + finish with resumption"), but there's no visibility into *why*
a CI gate is slow or what's currently running — a user has to separately open
GitHub Actions in a browser.

## Evidence

- `minibox/xtask/src/ci_watch.rs`: watches the latest GHA run with job-level
  detail, inferring repo/branch via `gh`/`git`.
- `taskit-engine/src/flow.rs`: `flow auto`'s CI-gate step (per recent
  telemetry work — `flow_auto_*` metrics emitted from `auto_with_ci`, commit
  `caf9d80`) currently only knows pass/fail + duration, not per-job progress.
- `taskit-tui`: the Flow tab (`docs/designs/2026-08-08-tui-flow-tab-design.md`)
  already renders `flow auto` telemetry and resumable state — a natural
  consumer for live per-job CI status if `ci-watch` existed.

## Proposed Direction

Add `taskit ci-watch` as a standalone command wrapping `gh run watch` /
`gh api` for job-level polling of the current branch's latest run, reusing
the `resolve_repo` helper already made `pub(crate)` in `release/gh.rs` this
session. Optionally wire it as an interactive detail view inside the TUI's
Flow tab rather than (or in addition to) a standalone CLI command.

## Open Questions

- Does this need to be interactive/blocking (like `gh run watch`), or a
  one-shot status snapshot consumable by the TUI's periodic refresh?
- Is this valuable as a general `taskit` feature, or specific enough to
  `flow auto`'s CI-gate step that it should just be inlined there instead of
  a separate top-level command?
